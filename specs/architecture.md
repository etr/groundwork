# Groundwork Architecture

## Parallel task-runner synchronization

The task runner coordinates through files under the repository common Git directory. Project leases live in `groundwork/projects/` and scope one full task lifecycle per project. The repository gate lives in `groundwork/repository-gate/`: token-named reader leases admit concurrent readers at short lifecycle call sites, `writer.lock` protects repository-wide mutations, and token-named `writers-waiting/` intents prevent reader barging while a writer is queued. Model phases (plan, implement, validate, finalize) deliberately do not hold the reader gate: each phase runs inside its own task worktree over its own branch under the per-task project lease alone, so a publication in another package never waits out a running phase.

Every lease transition — publication, stale reap, gate admission — runs inside a serialized mutation turn: a ticket queue in `groundwork/projects/<projectKey>.queue/` beside that project's lease (sharded per project so packages never serialize on one shared queue). Queue records carry a random token agreeing with their filename, PID, and process-start identity; a waiter reaps a predecessor ticket only when its holder process is provably dead, and every queue entry is validated fail-closed (bounded size, no symlinks, exact ownership shape) before it is trusted. Lease files are created atomically with exclusive creation and contain a random token, PID, process-start identity, bounded project identity, project-relative path, task ID, and timestamp. Token-named files must agree with their record. Stale removal is serialized by a recovery claim and revalidates the current file while holding that claim, preventing one reclaimer from unlinking a successor lease.

The runner prepares the task branch and linked worktree while holding the workspace-registry lease under a reader gate, then hands phases the per-task project lease only. Genuinely shared Git and base-checkout operations — startup checks, plan-ignore setup, workspace preparation and the worktree registry, completed-task cleanup, and publication — take the repository gate at their own call sites for exactly their duration; a phase never holds it. A phase snapshot protects all repository refs except the exact task refs belonging to verified live peer project leases. The runner similarly protects every checkpoint except those exact live peers. Full unrelated-worktree cleanliness scans occur at the writer-gated lifecycle boundaries rather than before and after every reader phase; this keeps concurrent phase waves linear instead of producing a scan matrix across all worktrees.

Publication acquires the writer gate and rechecks unrelated worktrees, the base head, validated task head, bookkeeping-only finalization diff, Git controls, and registered workspace identity. A base-head mismatch converts the READY result into revalidation without removing the branch or worktree. Only a successful verified merge may remove the workspace, delete the task branch, and clear the checkpoint.

### Runner reporting and status projection

`lib/run-reporting.js` is the reporting deep module. `bin/groundwork-run.js` owns lifecycle timing and provider-stream normalization, then passes only normalized activity or exact semantic signals to one reporter scoped to the acquired task lifecycle. The reporter owns event-envelope fields, sequence ordering, credential redaction, display-control rejection, rendering, and safe append descriptors; raw provider JSON remains ephemeral phase output and is never copied into durable reporting.

Reporting lives at `<git-common-dir>/groundwork/reporting/<project-key>/TASK-NNN/`, where `<project-key>` is the first 16 hexadecimal characters of the SHA-256 digest of the repository-relative configured project path (`.` for a single-project repository). `events.jsonl` is an append-only sequence of version-1 lifecycle envelopes; `runner.log` is the concise semantic projection; `transcript.jsonl` is a sequence of normalized diagnostic records without a raw provider envelope. The phase monitor worker appends transcript records while the synchronous harness child is still running, then closes and synchronizes the transcript before the parent accepts the phase result. Provider reasoning events are ignored. User-visible agent messages, reviewer batches, activity, semantic markers, and bounded tool output cross explicit type validation, credential redaction, control rejection, and truncation before persistence. All sinks use `O_APPEND|O_NOFOLLOW` and reject symlinks or non-regular files.

The `GROUNDWORK_RUNNER_EVENT ` marker is the provider-to-runner trust boundary. `parseRunnerMarker` accepts only exact version-1 type schemas and bounded categorical or redacted printable fields; ordinary prose, surplus keys, invalid ranges, controls, and unknown marker types do not become semantic state. Journal reads repeat exact event-schema validation and text sanitization, so forged or damaged append-only records cannot introduce categorical state, credentials, or terminal controls through status.

`groundwork-run status TASK-NNN` resolves the same project-keyed reporting path but does not enter the task lifecycle: it invokes no harness and acquires no project lease or repository gate. The status reader combines the newest coherent runner event sequence, the identity-bound validation-session snapshot, and the latest reviewer-batch transcript record to display the round, stage, and per-agent state without trusting reviewer prose. `groundwork-run logs TASK-NNN` reverse-scans the newest run's transcript for its initial tail and, with `--follow`, reads append-only records until the matching runner event sequence becomes terminal. Both readers refuse symlinks and invalid records and never repair, compact, append, or enter synchronization state.

### Recovery controller

Phase invocation and phase-specific receipt parsing share one recovery-aware operation. Explicit result failures and malformed successful-exit receipts therefore follow the same controller, while independently identified safety and identity violations remain hard failures. The controller has a constant two-session budget per failed phase: an initial fresh recovery session and at most one stronger fresh retry. Progress fingerprints inform diagnostics but never reset that total budget.

Recovery is a fresh repair session invoked through the same ungated phase path as an ordinary call: it runs inside the task worktree under the per-task project lease with no repository gate held across it, and a ready result retries the failed phase. Recovery creates no snapshots, rollback transaction, special commit, or repository-wide boundary comparison; repair changes remain in the worktree for the retried phase and its normal commit flow, and repair sessions never publish. Ordinary plan, implement, validate, and finalize calls carry only the per-task project lease — the repository reader gate is deliberately not held across a phase, because phases run inside their own task worktree over their own branch and a publication in another package must not wait out a phase.

Recovery result text is a routing hint rather than authority. Observed mutation or an explicit `revalidate` hint during finalization routes back through validation; `needs_user` without an independently observed hard or product-decision boundary does not stop the lifecycle. Once recovery succeeds, normal validation, finalization, publication, and later sequential tasks proceed unchanged.

`info/exclude` initialization is a writer-gated setup responsibility. In a configured monorepo, a runner installs all project plan-ignore entries in one update so later concurrent project setup does not mutate Git controls during another project's reader phase.

### Upgrade boundary

The repository-gate protocol is a v2-only protocol. Before installing or starting v2, operators must stop and drain every earlier-version runner process and launcher targeting the repository; hot mixed-version operation is unsupported. On startup, v2 inspects the predecessor's `groundwork/runner.lock` and fails closed if it detects a live, malformed, or stale record, preserving stale records for manual recovery. This inspection is best-effort defense and diagnostics, not an atomic coexistence guarantee: a predecessor can start after the check and cannot observe v2 reader leases. V2 therefore does not create `runner.lock` at writer boundaries, which preserves concurrent v2 reader phases rather than introducing a global legacy barrier.

The same drain-before-upgrade precondition covers the per-project mutation queues. `groundwork/projects/<projectKey>.queue/` replaced an earlier shared mutation queue at `groundwork/projects/.lease-mutation`: a pre-sharding runner and a post-sharding runner mutating the same project lease would serialize on different queues, so the read-verify-unlink reap window the queue exists to close would be unprotected across the version skew. Before acquiring a project lease, the runner therefore inspects the legacy shared queue and fails closed while it still holds queue records — a live record means a pre-sharding runner is still mutating; a stale record is preserved for manual recovery — and passes only on drained or absent legacy state.

### Model-process threat boundary

Linked worktrees, scoped leases, and post-phase snapshots protect against accidental or buggy model-phase mutations. They are not an isolation boundary against a hostile child process running as the same OS user: such a child can locate the Git common directory, external user configuration, or paths outside the observed repository and deliberately alter them. Writer exclusivity, boundary checks, and restoration cover the repository state the runner snapshots, but cannot guarantee containment or rollback outside that scope. Enforcing hostile-process isolation would require an OS sandbox or private clones outside the child-writable Git directory; the runner intentionally does not claim that stronger guarantee.
