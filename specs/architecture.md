# Groundwork Architecture

## Parallel task-runner synchronization

The task runner coordinates through files under the repository common Git directory. Project leases live in `groundwork/projects/` and scope one full task lifecycle per project. The repository gate lives in `groundwork/repository-gate/`: token-named reader leases admit concurrent model phases, `writer.lock` protects repository-wide mutations, and token-named `writers-waiting/` intents prevent reader barging while a writer is queued.

Lease files are created atomically with exclusive creation and contain a random token, PID, process-start identity, bounded project identity, project-relative path, task ID, and timestamp. Token-named files must agree with their record. Stale removal is serialized by a recovery claim and revalidates the current file while holding that claim, preventing one reclaimer from unlinking a successor lease.

The runner creates the task branch and linked worktree while holding the writer gate, then gives phase agents reader access. A phase snapshot protects all repository refs except the exact task refs belonging to verified live peer project leases. The runner similarly protects every checkpoint except those exact live peers. Full unrelated-worktree cleanliness scans occur at the writer-gated lifecycle boundaries rather than before and after every reader phase; this keeps concurrent phase waves linear instead of producing a scan matrix across all worktrees.

Publication acquires the writer gate and rechecks unrelated worktrees, the base head, validated task head, bookkeeping-only finalization diff, Git controls, and registered workspace identity. A base-head mismatch converts the READY result into revalidation without removing the branch or worktree. Only a successful verified merge may remove the workspace, delete the task branch, and clear the checkpoint.

### Recovery controller

Phase invocation and phase-specific receipt parsing share one recovery-aware operation. Explicit result failures and malformed successful-exit receipts therefore follow the same controller, while independently identified safety and identity violations remain hard failures. The controller has a constant two-session budget per failed phase: an initial fresh recovery session and at most one stronger fresh retry. Progress fingerprints inform diagnostics but never reset that total budget.

Recovery uses a dedicated writer-gated path; ordinary plan, implement, validate, and finalize calls remain reader-gated. The writer lease is held continuously while the runner captures the before-state, creates content-addressed filesystem and metadata rescue snapshots, invokes the recovery child, observes the after-state, checks repository boundaries, approves an exact path set, stages and verifies that set, creates the runner-owned recovery commit, invalidates validation, and updates the checkpoint. This removes the check-to-stage race and prevents peer readers or writers from overlapping any model-directed recovery observation or mutation.

The before/after observation separates full-fidelity local authorization data from model context. Locally, the runner hashes complete porcelain state and changed-file bytes, the primary and selected worktrees, unrelated registered worktrees, all refs, the worktree registry, Git controls and effective configuration/identity, runner state, and the selected checkpoint. The recovery prompt receives only bounded status summaries and hashes; diagnostic and state fields pass through centralized credential redaction and explicit UTF-8 byte caps, and are labeled as untrusted data.

The selected-worktree rescue stores the exact pre-recovery index plus every pre-existing dirty and untracked path. Metadata rescue covers repository configuration, hooks, attributes, worktree configuration, and runner checkpoints. A hard boundary restores protected metadata, refs, worktree registrations, and worktree bytes where the runner can deterministically reconstruct the prior state; the rescue and rejected-state snapshots remain available when user judgment is required. An accepted delta may contain only regular files under the selected configured project. It cannot delete a path, change an unsafe file type, or alter bytes that existed in the failed phase's dirty/untracked state. Sealing uses the approved path list rather than broad `git add -A`, then verifies the cached path set before commit.

Recovery result text is a routing hint rather than authority. Observed mutation or an explicit `revalidate` hint during finalization routes back through validation; `needs_user` without an independently observed hard or product-decision boundary does not stop the lifecycle. Once recovery succeeds, normal validation, finalization, publication, and later sequential tasks proceed unchanged.

`info/exclude` initialization is a writer-gated setup responsibility. In a configured monorepo, a runner installs all project plan-ignore entries in one update so later concurrent project setup does not mutate Git controls during another project's reader phase.

### Upgrade boundary

The repository-gate protocol is a v2-only protocol. Before installing or starting v2, operators must stop and drain every earlier-version runner process and launcher targeting the repository; hot mixed-version operation is unsupported. On startup, v2 inspects the predecessor's `groundwork/runner.lock` and fails closed if it detects a live, malformed, or stale record, preserving stale records for manual recovery. This inspection is best-effort defense and diagnostics, not an atomic coexistence guarantee: a predecessor can start after the check and cannot observe v2 reader leases. V2 therefore does not create `runner.lock` at writer boundaries, which preserves concurrent v2 reader phases rather than introducing a global legacy barrier.

### Model-process threat boundary

Linked worktrees, scoped leases, recovery rescue snapshots, and post-phase snapshots protect against accidental or buggy model-phase mutations. They are not an isolation boundary against a hostile child process running as the same OS user: such a child can locate the Git common directory, external user configuration, or paths outside the observed repository and deliberately alter them. Writer exclusivity, boundary checks, and restoration cover the repository state the runner snapshots, but cannot guarantee containment or rollback outside that scope. Enforcing hostile-process isolation would require an OS sandbox or private clones outside the child-writable Git directory; the runner intentionally does not claim that stronger guarantee.
